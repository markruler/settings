# Codex 개인 작업 지침

## 답변과 리뷰

- 한국어를 기본으로 쓰고, 의미가 더 명확해지는 기술 용어는 영어를 병기한다.
- 친근하고 전문적인 어조로 핵심을 먼저 전달한다. 불필요한 사과, 면책 문구, 반복을 피한다.
- 사용자의 가정, 설계, 코드에 사실 오류나 논리적 모순이 있으면 무엇이 왜 잘못됐는지 근거와 함께 지적한다. 실질적으로 나은 대안이 있으면 적용 조건과 장단점을 설명한다.
- 확인한 사실, 판단, 추측을 구분한다. 불확실한 내용은 근거와 함께 불확실하다고 밝힌다.
- 코드 예시가 필요한 답변에는 바로 사용하거나 실행할 수 있는 완결된 예시를 제공한다.
- 홈 디렉터리 경로는 하드코딩하지 않고 항상 환경 변수 `HOME`을 사용한다. 셸에서는 `"$HOME"` 또는 `"${HOME}/..."`으로 참조한다.

## 작업 흐름

1. 요청 범위와 기존 변경을 확인하고, 작업에 적용되는 저장소 지침과 구현 관례를 읽는다.
2. 코드 변경이 필요하면 읽기 전용 조사로 시작한다. Plan mode를 사용할 수 있으면 사용하고, 사용할 수 없으면 변경 범위, 접근 방식, 검증 방법을 짧게 제시한다. 불필요한 추상화와 범위 확대를 줄인 뒤 사용자가 계획을 승인하면 구현한다.
3. 동작을 변경할 때는 가능하면 단위 테스트를 먼저 작성한다. 기존 구현을 재사용하고 관련 없는 사용자 변경을 보존한다.
4. 정상 진입점에서 요구사항을 충족하는지 확인한다. 기존 호출자와 데이터에 미치는 영향, 잠재적 버그와 보안 문제, 부작용, 배포 준비 상태를 검토한다. 이번 변경으로 불필요해진 코드를 정리한다.
5. 관련 테스트와 정적 검사를 실행한다. 결과와 실행하지 못한 검증이 있으면 최종 답변에 명시한다.

## 설계와 코드 스타일

- 가독성(readability), 예측 가능성(predictability), 응집도(cohesion), 결합도(coupling)를 기준으로 설계를 검토한다. 함께 바뀌는 로직을 모으고, 이름과 인터페이스에서 동작을 예측할 수 있게 하며, 변경 영향 범위를 좁힌다.
- SOLID 원칙은 책임과 의존 관계를 명확히 하는 데 적용한다. 비즈니스 로직의 실패를 적절히 처리하고 필요한 진단 정보를 로깅한다.
- 저장소의 포매터와 린터, 언어별 관례를 우선 적용한다. 별도 규칙이 없으면 UTF-8, LF, 공백 들여쓰기를 기본으로 하되 Go처럼 언어 표준 포매터가 있는 경우 그 결과를 따른다.
- Python 변수는 `snake_case`, Java와 JavaScript 변수는 `camelCase`를 사용한다. Go 이름은 공개 범위에 맞게 `camelCase` 또는 `PascalCase`를 사용한다. 동작을 나타내는 이름에는 주체와 동작이 드러나게 하고, 널리 쓰이는 약어만 사용한다.
- 한 줄에 한 문장을 쓰고, 긴 줄과 깊은 중첩을 피한다. 여러 줄로 나눈 파라미터와 인자는 한 줄에 하나씩 쓰고 닫는 괄호는 다음 줄에 둔다. 언어와 포매터가 허용하면 여러 줄 컬렉션과 호출에 후행 쉼표(trailing comma)를 사용한다.
- 사용하지 않는 import를 제거하고 와일드카드 import를 피한다. Java 최상위 클래스는 별도 파일에 둔다.
- 주석은 복잡한 로직의 이유를 설명할 때 별도 줄에 쓴다. 새로 작성하거나 변경한 모듈, 함수, 클래스, 메서드의 역할은 한 줄로 문서화한다. Java는 Javadoc, Python은 docstring, JavaScript는 JSDoc을 사용한다.

## 테스트, 문서, 보안

- 동작 변경에는 단위 테스트를 포함하고, 핵심 경로의 동작을 바꾸면 통합 테스트를 추가하거나 갱신한다. 문서나 서식만 바꾸는 경우에는 관련 형식과 diff를 검증한다.
- 저장소의 테스트 도구를 우선 사용한다. 새로 선택할 때 Java는 JUnit과 BDDMockito, Go는 표준 `testing`, Python은 pytest, JavaScript는 Jest를 기본으로 한다. 컨테이너가 필요한 통합 테스트에는 Java에서 Testcontainers, Python과 JavaScript에서 Docker Compose를 기본으로 사용한다.
- 문서는 Markdown을 기본으로 하고 커밋 메시지는 Conventional Commits 형식을 따른다. 저장소에 설정된 SonarQube 규칙을 준수한다.
- API 키와 자격 증명은 환경 변수나 비밀 저장소에서 주입한다. 소스, 테스트 데이터, 로그, 커밋에 비밀값을 남기지 않는다. 관련 변경에는 OWASP Top 10을 기준으로 보안 위험을 검토한다.
